# 离线数据摆渡系统（FDT）细化技术方案

版本 v0.1 · 2026-10-21 · 状态：设计评审稿

---

## 0. 设计原则（不可违背的硬约束）

1. **完全离线 / 零出口**：内网无任何到互联网或 DMZ 的网络出口。内网与外部之间**只有二维码**这一条人肉摆渡通道。
2. **文件数据永不出内网**：跨区传递的只有带签名的**元数据令牌**。原始文件只在内网服务器 ↔ U盘之间流动。
3. **无例外通道**：所有密级（含极高密级）审批人只看到**文件清单**，绝不预览真实文件内容，不上 VDI、不落 DMZ 预览库。
4. **清单制内容可见性**：审批人看到"文件名/大小/类型/SHA256 + 压缩包成员清单 + DLP 定级"，据此审批；安全绑定靠 **Merkle 根**（与文件数无关，永不退化）。
5. **真实可用**：所有端口、地址、密钥、状态、哈希均为真实计算，无模拟值、无伪造硬件数据。

## 1. 系统组成与部署拓扑

```
┌─────────────────────── 内网区（气隙隔离，零出口）───────────────────────┐
│  ① 上传 Portal（Web）      ② 数据暂存/密级库       ③ 清单生成管线        │
│  ④ 审计与状态服务（申请单/核销CAS/审计哈希链）      ⑤ 签名服务(持SK_内网)  │
│  ⑥ 摆渡终端 ATM（Kiosk + 扫码枪 + USB口）多台       ⑦ 内网 CA/设备证书     │
│  所有组件走内网 LAN，仅 ATM/Portal ↔ 审计服务、ATM ↔ 数据服务 互通         │
└──────────────────────────────────────────────────────────────────────┘
        ▲ QR#1（申请令牌·单帧，人肉带出）        ▲ QR#2（放行令牌·单帧，人肉带回）
        │                                        │
   ┌────┴───────────── 用户手机（互联网）──────────┴────┐
   │  飞书小程序 scanCode 扫QR#1 → 网关后端验签建审批     │
   └──────────────────────────┬──────────────────────────┘
                              │ 飞书 OpenAPI + 事件回调（验签/mTLS/限源）
                     ┌────────┴──────────┐
                     │ ⑧ DMZ 审批网关     │  ← 唯一联网组件，只碰元数据
                     │ HSM(持SK_网关)     │  ← 建审批/收回调/签QR#2
                     └────────────────────┘
```

> 关键：内网服务器**永远不会知道**飞书是否审批通过（无回调入口）。审批的唯一凭证是 QR#2 本身，由 ATM 离线验签。因此内网申请单不存在"已审批"这一由回调驱动的状态（见 §7）。

## 2. 技术选型建议

| 组件 | 选型 | 理由 |
|---|---|---|
| 上传 Portal / 审计服务 / 清单管线 / 签名服务 | Go + PostgreSQL + React 前端 | Go 哈希/流式吞吐高、单二进制易部署；PG 事务保证核销 CAS |
| 密码学 | Ed25519（签名）+ SHA-256（哈希）+ libsodium | Ed25519 签名 64B、公钥 32B，省 QR 空间 |
| HSM | PKCS#11 接口（如支持国密则 SM2/SM3 可选） | 网关私钥硬件保护 + 双控 |
| DMZ 网关 | Go/Node + 飞书开放平台 SDK | 轻量，仅元数据 |
| ATM Kiosk | Go 后台代理 + 本地 Web UI（webview）+ udev | 直接访问 USB/HID、易锁定 |
| QR 生成/识别 | segno（内网生成单帧 QR）；识别走**飞书小程序 `scanCode`**（单码） | 单帧方案，无需连续读帧 |
| 令牌编码 | CBOR（规范化）→ deflate 压缩 → base45（单帧 QR） | 紧凑、确定性、二维码友好 |
| DLP / AV | 可插拔（对接现有 DLP/杀软引擎） | 内网侧对数据与导入 U盘扫描 |

## 3. 密码学与密钥体系

### 3.1 密钥

| 密钥 | 位置 | 用途 | 保护 |
|---|---|---|---|
| `SK_内网 / PK_内网` | 内网签名服务（离线） | 签 QR#1 申请令牌 | 内网 HSM 或加密密钥文件，物理隔离 |
| `SK_网关 / PK_网关` | DMZ 网关 HSM | 签 QR#2 放行令牌 | **HSM + 签名双控（two-person）**，定期轮换 |
| 设备证书 | 内网 CA 签发，每台 ATM 一张 | ATM ↔ 内网服务双向认证 | TPM/安全存储，防假 ATM |

- 公钥分发：网关存 `PK_内网`（验 QR#1）；每台 ATM 离线烧录 `PK_网关`（验 QR#2）+ 设备私钥。
- 签名算法统一 Ed25519；哈希 SHA-256；令牌含 `kid` 支持轮换。

### 3.2 Merkle 树（安全绑定的核心）

- 叶子 = 每个文件的 `SHA-256(file)`（按清单排序，规范化路径）。
- 内部节点 = `SHA-256(left || right)`；奇数节点复制自身配对。
- 根 = `merkleRoot`（32B），**恒定大小，与文件数无关**。
- 用途：
  - QR#1/QR#2 都携带 `merkleRoot`，审批绑定的是"这组精确指纹"。
  - ATM 写盘时对每个文件流式算 SHA-256 重建 Merkle 根，与令牌根比对，一致才核销。
  - 大清单降级为摘要模式时，逐文件哈希仍全部入库（内网留存），根哈希保证任何替换都会被拦截。

## 4. 清单与令牌数据结构

### 4.1 文件清单条目（内网全量留存）

```jsonc
// request_files 表逐行；同时构成 Merkle 叶子
{
  "path": "project/src/main.go",   // 规范化相对路径
  "size": 20480,
  "type": "text/x-go",             // 由魔数/MIME 探测
  "sha256": "…64hex…",
  "leaf": 12,                      // Merkle 叶序号
  "inArchive": null                // 若来自压缩包，记 "outer.zip#inner/path"
}
```

### 4.2 QR#1 申请令牌（内网 SK_内网 签）

```jsonc
{
  "v": 1, "kid": "int-2026-01",
  "reqId": "uuid",
  "dir": "export",                 // export | import
  "applicant": {"id": "e1234", "name": "张三", "dept": "设计部"},
  "reason": "交付客户A的版图数据",  // 事由摘要（出外网，注意脱敏）
  "cls": "secret",                 // 密级
  "dataset": {
    "count": 1523, "totalSize": 4831838208,
    "merkleRoot": "…64hex…",
    "mode": "summary",             // full | summary（见 §5.2）
    "dlp": {"categories": {"个人信息": 3, "源代码": 120}, "av": "clean",
             "hits": ["…"]},        // DLP/AV 摘要
    "entries": [ {"p":"…","s":20480,"t":"text/x-go","h":"…前128bit…"} ], // 仅 full 模式（装得进单帧时）
    "tree": [ {"n":"project","c":1523,"s":4831838208,"mr":"…","ch":[…]} ] // summary 模式
  },
  "nonce": "…16B…", "iat": 1760000000, "exp": 1760000900  // 有效期分钟级
}
```

### 4.3 QR#2 放行令牌（网关 SK_网关 签，单帧即可）

```jsonc
{
  "v": 1, "kid": "gw-2026-01",
  "reqId": "uuid",
  "merkleRoot": "…64hex…",          // 必须与 QR#1 一致
  "fsApprovalId": "飞书审批实例ID",
  "approver": {"id":"…","name":"李四"},
  "dir": "export",
  "nonce": "…", "iat": …, "exp": …   // 短有效期
}
```

### 4.4 令牌编码（单帧，无动画）

采用 **B 方案**：QR#1 永远单帧，不用动画多帧、不用浏览器页。

```
blob   = deflate( CBOR(token) || ed25519_sign(SK, CBOR(token)) )
QR内容  = "FDT1." + base45(blob)          // 单帧，控制在 ≤ ~1.8KB 可靠扫描区
```

- QR#1 与 QR#2 均为**单帧**。飞书小程序 `scanCode` 扫一次即得完整 token 字符串。
- 单帧容量预算 ~1.8KB 决定 QR#1 能带多少明细（见 §5.2）：装得下就带逐文件清单，装不下就只带摘要——**但 token 永远单帧**。
- 接收端（网关后端）：base45 解码 → inflate → 拆 payload+sig → 用 `PK_内网` 验签 → 校验 `merkleRoot` 自洽 → 建飞书审批。

## 5. 清单生成管线（内网侧）

### 5.1 流程

```
上传/插入 → 落暂存区(只读) → 递归遍历 → 逐文件 SHA-256 → 探测类型(魔数)
        → 压缩包安全展开(§5.3) → DLP 定级 + AV 扫描 → 构建 Merkle 树
        → 按 count 选 mode(§5.2) → 生成清单 → 全量逐文件清单入库
        → 组装 QR#1 token → SK_内网 签名 → 编码分帧
```

- **异步 + 进度**：大目录/大压缩包遍历与哈希很重，走后台任务队列，Portal 实时显示进度（已扫描 N/总数、速率），并预告"审批人将看到：完整清单 / 仅摘要"（取决于是否装进单帧）。
- **增量/缓存**：上传时即算并缓存每文件哈希，导出时 ATM 复用，避免重复全量哈希。

### 5.2 单帧预算下的分级策略（能否装进单帧自动切换）

因为 QR#1 恒定单帧（≤~1.8KB），装多少明细由**预算**决定，不再用多帧：

| 规模 | mode | QR#1 内容（均单帧） | 逐文件全量清单 |
|---|---|---|---|
| 明细压缩后 ≤ 预算 | `full` | 全量 entries（路径前缀压缩 + 哈希截断 128bit），约可容 30–50 个文件 | 出内网（随 QR） |
| 超出预算 | `summary` | 总数/总大小/顶层目录树（各目录 count/size/子 Merkle 根）+ DLP 分布 + 全量 merkleRoot | **仅内网留存**，不出网 |

- 判定：清单管线生成后先算压缩体积，装得下走 `full`、装不下自动降级 `summary`；**两种都是单帧、都走飞书小程序扫码**，无浏览器页、无动画。
- **残留（B 方案已接受）**：大压缩包/海量文件时审批人只看到摘要（结构+统计+DLP+Merkle根），**看不到逐文件名**；完整清单仅内网审计留存。安全绑定仍由 merkleRoot 保证，不退化。
- **护栏**：设单次摆渡 `文件数上限`/`数据量上限`；超限要求拆分申请；提交前明确显示"审批人将看到：完整清单 / 仅摘要"。

### 5.3 压缩包安全展开（沙箱）

- 支持 zip/tar/gz/bz2/xz/7z/rar（只读）。
- 防护：**解压炸弹**（限展开总字节数、压缩比、递归深度）、**嵌套包**（限层数）、**路径穿越**（`../` 拦截）、**符号链接**（不跟随）。
- **加密包**：无法列成员 → 标注 `"加密-无法列出"`，只给整包 size+sha256，走人工/特殊审批提示。
- 展开只为"生成清单"，绝不还原落盘为可执行；成员哈希用于纳入 Merkle。

## 6. 组件接口（内网）

| 服务 | 关键接口 | 说明 |
|---|---|---|
| 上传 Portal | `POST /requests`(建单+上传) `GET /requests/{id}/qr1`(取单帧QR#1) `GET /me` | Basic-Auth(AD/LDAP) 保护；返回进度与"完整清单/仅摘要"提示 |
| 清单管线 | 内部异步任务 | 遍历/哈希/DLP/Merkle/单帧编码 |
| 签名服务 | `sign_qr1(token)`, `sign_qr2_import(token)` | 持 SK_内网，导入 QR#1 也由此签 |
| 审计/状态服务 | `create_request` `claim(reqId,atmId,ttl)` `consume(reqId,nonce,atmId,usbSerial,hash)` `log(event)` | 核销 CAS + 租约 + 审计哈希链 |
| 数据服务 | `GET /requests/{id}/stream`（ATM 拉数据流） | 仅对已认证 ATM 开放 |
| ATM Kiosk | 本地 UI + 上述客户端 | 见 §9 |

**申请人身份（AD/LDAP，`internal/identity`）**：Portal 经 HTTP Basic 收域账号口令，用 `LDAPProvider` search-then-bind 向域控验证并读取 `displayName/employeeID/department`；**认证身份覆盖前端传值**写入 QR#1 的 applicant 并随令牌签名，杜绝冒充，并支持按部门/密级路由审批。Basic 与 LDAP 均须走 TLS；用户名进过滤器前 `ldap.EscapeFilter` 转义防注入；服务账号只读最小权限。离线开发用 `MockProvider`（`-identity mock`）。DC 在内网，属同区流量，不违反零出口。

**导出兑付时序（ATM 侧）**：
```
插U盘(检测/预检) → 扫QR#2 → 验签(PK_网关)+校验exp → claim租约(防并发双写)
→ 从数据服务流式拉取 → 边写U盘边算每文件SHA256 → 重建merkleRoot比对令牌
→ 一致: fsync → 回读U盘重算校验 → consume(CAS核销) → 写审计 → 提示可拔盘
→ 不一致/拔盘/IO错误: 删除半成品 → 回滚 → 释放租约 → 告警(不核销, 令牌仍有效)
```

## 7. 申请单状态机（零出口下的精确状态）

**内网可见状态**（内网无回调入口，故无"已审批"态）：

```
导出: DRAFT → PENDING_APPROVAL → REDEEMED(终态)
                                 ↘ EXPIRED / CANCELLED
导入: DRAFT → PENDING_APPROVAL → QUARANTINED → SCANNING → RELEASED(终态)
                                          ↘ BLOCKED(命中病毒/DLP)
      ↘ EXPIRED / CANCELLED
```

- `PENDING_APPROVAL`：QR#1 已生成，等待外部审批（内网不知结果）。
- `REDEEMED`：ATM 成功落盘并 CAS 核销（终态、不可逆）。
- 审批结果只存在于网关/飞书侧，通过 QR#2 携带 `fsApprovalId`+`approver` 进入内网审计记录（事后关联）。

**核销并发控制（对应"落盘才失效"+"不绑定身份"）**：
1. `claim(reqId, atmId, ttl=90s)`：写盘前抢短租约，第二台 ATM 收到"兑付进行中"，收窄并发双写窗口。
2. 写盘 + 校验成功后 `consume`：`UPDATE tokens SET consumed=true WHERE reqId=? AND consumed=false`，检查影响行数=1。
3. 若=0（已被他机核销）→ 本机写盘属**重复导出事件**，告警并记审计（数据已从另一U盘流出，属安全事件）。
4. **失败不消耗**：没插盘/容量不足/写保护/IO错误/中途拔盘/校验不符 → 不 consume，令牌保持有效可再兑付。

## 8. 飞书对接（飞书网页应用 + DMZ 网关后端）

采用 **B 方案**：以**飞书网页应用（H5）**为载体，在飞书客户端内打开，**不使用动画多帧**。（原小程序路径因飞书 2025 年起对新租户关闭新建入口而改为网页应用；`scanCode` JSAPI 仍可用。H5 由网关托管在 `/app/`。）

1. **前置**：飞书自建应用（审批权限）+ 自定义审批流模板；开启**网页应用**，主页 `https://<gw>/app/`，配置 H5 可信域名。
2. **扫码发起**：用户在 Portal 得到单帧 QR#1 → 打开网页应用 → JSAPI 鉴权后 `scanCode` **扫一次** → H5 把 token POST 给网关 `/submit`。
3. **建审批**：网关后端 base45 解码 + `PK_内网` 验签 + 校验 merkleRoot → 调 `创建审批实例`（approval v4），把清单/摘要渲染进表单；保留 `reqId ↔ instanceId` 映射。
4. **审批与出码**：审批人在飞书审批；H5 轮询 `/qr2`；通过后网关 HSM 双控签 QR#2，页面展示 `/qr2/png` 供用户到 ATM 扫。
5. **回调验签（关键，对应 C3）**：飞书事件回调必须
   - 校验事件签名 / 解密（Encrypt Key + Verification Token）；
   - 校验来源 IP 白名单 + mTLS；
   - 校验 `instanceId` 属于本网关创建、状态确为 APPROVED；
   - 通过后才触发 HSM 双控签名生成 QR#2。
6. **网关绝不接触文件**，只有 QR#1 带来的元数据；审批结束清除临时元数据。

> 为什么坚持单帧 + `scanCode`：自定义 camera 连续扫码不可靠，而官方 `scanCode` 单码识别稳定可用（网页应用与小程序均支持）。B 方案把 QR#1 恒定为单帧。

## 9. ATM Kiosk 详细设计

### 9.1 状态机（强制"先插盘后扫码"）

| 状态 | 界面 | 扫码枪 | 转移 |
|---|---|---|---|
| `空闲·无U盘` | "请插入U盘" | **拒绝**，提示"未检测到USB存储设备" | 插入→就绪 |
| `就绪·有U盘` | 容量/可写/文件系统 | **允许** | 扫码→校验中 |
| `校验中` | 转圈 | 屏蔽 | 成功→写入中 / 失败→错误 |
| `写入中` | 进度+百分比+速率 | 屏蔽 | 完成→完成 / 拔盘→错误(回滚) |
| `完成` | "✅ 可安全拔出U盘" | 屏蔽 | 拔盘→空闲 |
| `错误` | 具体原因+错误码 | 屏蔽 | 确认→空闲/就绪 |

### 9.2 USB 处理与安全（对应 H1/H3/M4）

- **热插拔**：udev 监听；插入后**先只读挂载**探测。
- **设备白名单**：仅放行 USB Mass-Storage 类；**拒绝 HID/复合设备**（防 BadUSB 键盘注入）；按 VID/PID/类过滤。
- **预检**：容量 ≥ 数据大小、非写保护、文件系统支持大文件（FAT32 单文件 >4GB 提示 exFAT/NTFS）。
- **写盘**：数据流经 tmpfs 内存盘或直管到 U盘，**不落 ATM 本地磁盘**；边写边算 SHA-256；写完 fsync → **回读重算 Merkle 根**比对；临时空间用后安全擦除。
- **拔盘/掉电**：立即中止 + 删除半成品 + 回滚 + 告警，不核销。

### 9.3 扫码枪输入（对应 H1 命令注入）

- **强烈建议扫码枪配置为 USB CDC/虚拟串口模式**（非 HID 键盘），从根上杜绝按键注入。
- 若只能 HID：应用**独占抓取输入**到隐藏缓冲，内容仅当**纯数据**解析（必须匹配 `FDT1|…` 或 QR#2 格式），**绝不喂入 shell/命令行**；过滤控制字符。
- 二维码内容一律走结构化解析 + 验签，非法即拒。

### 9.4 Kiosk 锁定

- 全屏单应用自启 + 看门狗；禁用 shell/tty/快捷键/任务管理器；禁蓝牙/WiFi/其他外设。
- USB 端口：`authorized_default=0`，仅授权指定数据口。
- 网络：仅允许到内网审计/数据服务的白名单，其余全禁。
- 设备证书双向认证接入内网服务，未注册设备（假 ATM）无法联网取数（对应 M1）。

### 9.5 导入模式（对称）

```
插源U盘 → 只读索引 → 逐文件SHA256+清单 → 请求内网签名服务签 QR#1(dir=import)
→ 手机扫码走飞书审批 → 扫 QR#2 验签 → 校验哈希与索引时一致(防审批后换盘)
→ 拷入内网隔离区(非最终目录) → 强制 AV/DLP 扫描
→ 通过: 释放到目标目录, 状态 RELEASED, 写审计
→ 命中: BLOCKED, 拦截告警, 不释放
```

requests(
  id uuid pk, dir text, applicant_id text, applicant_name text, dept text,
  reason text, cls text, status text,               -- §7 状态
  file_count int, total_size bigint, merkle_root char(64),
  manifest_mode text, dlp_summary jsonb, av_status text,

)
tokens(
  request_id uuid fk pk, qr1_nonce text, qr2_nonce text,
  qr2_exp timestamptz, lease_atm uuid, lease_until timestamptz,
  consumed bool default false, consumed_at timestamptz, consumed_atm uuid
)

  id uuid pk, name text, location text, cert_fingerprint text, status text
)

## 11. 安全控制 ↔ 风险矩阵对照

| 风险 | 缓解（本方案落点） |
|---|---|
| C1 QR#2 抢兑 | 分钟级 exp + claim 租约 + 落盘才核销 + 审计兑付 ATM；**接受残留**（不绑定身份为用户决策） |
| C2 SK_网关 单点 | HSM + 签名双控 + 轮换 + 网关最小化加固（§3.1/§8） |
| C3 回调伪造 | 飞书事件验签 + 限源 IP + mTLS + instanceId 归属校验（§8.4） |
| C4 语义鸿沟 | 清单可见 + **Merkle 哈希绑定**（批准=精确指纹）+ DLP 定级 + 高密级文件名脱敏；**无内容预览**（用户决策，残留永久接受） |
| H1 HID/BadUSB 注入 | 扫码枪串口模式/独占抓取、纯数据解析、USB 设备类白名单禁 HID（§9.2/§9.3） |
| H2 元数据明文 | 令牌可加 JWE 加密载荷（签名内含）；事由/文件名高密级脱敏 |
| H3 ATM 缓存残留 | tmpfs 直写不落盘 + 用后安全擦除 + 回读校验（§9.2） |
| H4 U盘失控 | 可选加密导出（口令/证书另渠道）+ 水印 + 记录 USB 序列号问责 |
| H5 状态/时钟 | nonce + 一次性核销（不只靠时间）+ 内网 NTP |
| M1 假 ATM | 设备证书双向认证，未注册无法取数（§9.4） |
| M2 ID 枚举 | reqId 用随机 UUID |
| M4 掉电部分写 | 回滚 + 回读校验（§9.2） |
| M5 审计伪造 | 审计哈希链 + WORM（§10） |

## 13. 多租户 / SaaS（共享网关 + 小程序）

目标：**一套共享的 DMZ 网关 + 一个飞书小程序服务多个客户**，客户只需在自己内网部署 Portal/datasvc/store/ATM（这半套因气隙必须 on-prem，无法托管）。同时**保留自部署单租户**开关，高敏客户可独占网关。

### 13.1 租户标识与路由

- QR 帧格式扩展为 `FDT1.<tenant>.<base45(...)>`：`<tenant>` 是**明文**段，网关据此**先选对该租户的 `PK_内网` 再验签**。
- 令牌**签名载荷内也含 `tenant` 字段**；`token.Open*` 交叉校验明文段与签名内 tenant 一致，**防止篡改租户前缀冒充/串路由**（`ErrTenantMismatch`）。
- 每个客户内网 Portal 配 `-tenant <id>`，写进它签发的 QR#1。

### 13.2 网关租户注册表

`gateway.Service` 持 `tenant → TenantConfig{PK_内网, SK_网关 signer, feishu.Client, feishuTenantKey}`：
- `SubmitQR1`：`PeekTenant` → 选租户 → 用该租户 `PK_内网` 验签 → 用该租户飞书客户端建审批。
- 会话按租户隔离；`mintQR2` 用**该租户的 `SK_网关`** 签，QR#2 也带 tenant。
- **每个客户的 ATM 只信任自己那把 `PK_网关`**：即便共享网关，A 的 QR#2 用 B 的 `PK_网关` 验不过（已测试）。
- 回调按 `/callback/{tenant}` 路由到对应租户客户端验签（自建应用各自 Encrypt Key；ISV 用 vendor 客户端）。

### 13.3 飞书形态：ISV / 商店应用（多客户公司）

- 不同客户 = 不同飞书组织，**单个自建应用无法跨组织**。SaaS 用**飞书 ISV/商店应用**：vendor 一个应用，各客户组织安装授权。
- `feishu.ISVClient`：vendor 应用 + **按客户组织的 `tenant_access_token`**（经 `TenantTokenSource` seam 注入，operator 实现 app_ticket→token 流程）；`CreateInstanceRequest.FeishuTenantKey` 指定目标组织；内部维护 `instanceID→tenantKey` 以支持状态查询。
- 若某客户愿用**自己的自建应用**，则该租户配 `feishu.LiveClient`（每租户一套凭据），与 ISV 混用皆可。
- 小程序：一个共享小程序，作为**商店应用**发布，各客户组织安装；`gatewayBase` 指向共享网关；扫码后按帧内 tenant 由网关路由，小程序无需按租户配置。

### 13.4 信任权衡（务必向客户说明）

- **信任集中**：所有租户都信任共享网关的 `SK_网关` 来"证明审批通过"，且网关能看到各租户的**清单元数据**（文件名/事由/申请人/Merkle根）。
- **风险边界**：网关被攻破/作恶只能对"见过的申请"伪造 QR#2，**拿不到数据**——数据在客户内网、兑付需到该客户 ATM 物理插 U 盘。危害限于"让已有待批申请的内部人跳过审批"，受气隙+物理接触限制。
- **缓解**：每租户独立 `SK_网关`（HSM 不同 label）、严格租户隔离、网关加固与审计、元数据最小化/高密级文件名脱敏；**高敏客户用自部署单租户网关**（同一套代码，`-tenants` 只配一个或用单租户 flag）。

### 13.5 配置

- 多租户：`fdt-gateway -tenants config/tenants.json`（见 `config/tenants.example.json`）。
- 自部署单租户：`fdt-gateway -internal-pub ... -gateway-key ... [-mock | -feishu-*]`（租户 id 固定 `default`）。
- 客户内网 Portal：`fdt-portal -tenant <id> ...`。
